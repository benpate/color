# color — Notes for AI Agents

Small library for parsing CSS-style color strings and transforming them through a chainable API. See [README.md](README.md) for the pitch. Emissary exposes it to templates as the `parseColor` funcmap function (returning a `color.Color` whose methods like `.Hex`, `.Text`, `.Mix`, `.IsDark` are then called from theme stylesheets, notably in bandwagon), so changes to method behavior ripple into rendered CSS.

- **Parsing never returns an error — invalid input yields the "empty" color, silently.** `Parse`, `ParseHex`, and `ParseRGB` all fall back to `NewColor()` (channels set to the sentinel `-1`), and `String()` on an empty color returns `""`. Downstream templates rely on this: a bad user-entered color degrades to empty output, not a render failure. Do not add error returns or panics.
- **The empty sentinel is `-1` channels, so the zero value `Color{}` is NOT empty — it is black with Opacity 0.** `Color{}` renders as `rgba(0,0,0,0)` (invisible black) and `IsEmpty()` reports false. Always construct through `NewColor()`, `Parse`, or the `White`/`Black` vars, never a bare struct literal. `Hex()` also emits malformed output (missing channel pairs) for hand-built structs with channels outside 0-255, because `formatHex` returns `""` out of range.
- **`ParseHex` accepts ONLY 6-digit hex, with or without `#`.** Three-digit shorthand (`#fff`), 8-digit hex-with-alpha, and named colors (`red`) all parse as empty. `ParseHex` never sets opacity; it is always 1.
- **`ParseRGB` cannot parse channel values above 127, and cannot handle spaces after commas.** [color-rgb.go](color-rgb.go) uses `strconv.ParseInt(value, 10, 8)` — bitSize 8 caps at 127, so `rgb(200,100,50)` comes back empty — and channel strings are not trimmed, so `rgb(1, 2, 3)` fails on `" 2"`. The existing tests only exercise channels 1-3, so nothing catches this. In practice the hex path carries nearly all real traffic; if you fix this, use bitSize 16 (with the existing 0-255 range check in `isValidInt`) plus `strings.TrimSpace`, and add tests above 127.
- **`rgba()` with an out-of-range or malformed alpha stores `Opacity: -1` on an otherwise-valid (NotEmpty) color.** `parseFloat` returns `-1` on failure and nothing validates it afterward, so `String()` can emit `rgba(r,g,b,-1)`. Emptiness checks look only at the RGB channels, never opacity.
- **Mixing truncates, it does not round, and tests lock that in.** `mix` in [color-manipulate.go](color-manipulate.go) casts through `int()`, so a 50% black/white mix is `#7f7f7f` (127), not `#808080`. `Mix` also keeps the receiver's Opacity and ignores the other color's, clamps percent to 0-100, and treats empty operands leniently (empty receiver returns the other color; empty other returns the receiver).
- **Light/dark decisions use the arithmetic mean of R+G+B against 127, not perceptual luminance.** `Mean`, `ColorMode`, `Text`, and `TextExt` all share this simple model on purpose; do not swap in WCAG luminance weights without Ben asking, since theme output (which text color sits on which background) would shift across every site.
- **`Mix(other any, ...)` re-parses its argument through `Parse`,** so templates can pass a hex string, an `rgb()` string, a `Color`, or a `*Color` interchangeably; any other type is treated as empty and leaves the receiver unchanged.
